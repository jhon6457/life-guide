# 监督与交接协议

本 Skill 可在三种工作方式下运行，按宿主实际能力如实选择，不得混称。

## 三种方式

1. **独立监督**：宿主提供独立子 Agent 时，主 Agent 承担监督——把检索、计算或起草交给子 Agent，收到结果后独立复核关键依据，再形成最终答复。
2. **顺序自检**：没有独立子 Agent 时，由同一 Agent 按本协议的清单逐项自检，并**如实说明这是顺序自检，不是独立复核**。
3. **审查模式**：用户或另一 AI 提交一份工作产出（研究、测算、建议稿）请求把关时，按本协议审查，出具通过或打回意见。

## 分工

工作侧负责理解问题、检索资料、扩展候选、计算、形成初步判断和行动建议；监督侧按下节流程与"打回清单"逐项复核，必要时退回重做。同一份清单服务两种方式，不在别处重复维护。

## 工作流程

1. 读取任务与已有资料，明确目标、硬约束和已授权范围；
2. 先交研究计划与关键未知清单（按 `gap-map.md`），再执行检索与计算；
3. 交付时附：来源与日期、计算过程、完整回答、未覆盖部分；
4. 监督方独立复核：抽查关键来源原文、复算关键数字、按 `gap-map.md` 检查缺口、按下方清单判断是否打回；
5. 打回时写清六件事（见下）；修正后再次复核；通过后才形成最终答复。

## 完成证据

以下**不构成**完成证据：口头声称"已核实""应该没问题"；格式或结构校验通过；关键词命中；"报告里说已完成"。

以下**才是**：实际文件与原文；实际来源与日期；实际计算与可复算的脚本；实际命令与输出；完整原始回答；可复现的运行记录（逐字输入、宿主、模型或"未知"、加载方式、判定理由）。判断同一模型下是否稳定时，至少重复三次相同输入，并固定模型、宿主、技能版本或哈希、加载方式和工具权限；任何条件变化都要单独标记。一次通过只能证明一次运行，不得写成稳定效果。

## 打回清单（出现即打回）

- 用户目标或硬约束未弄清就开始个性化推荐；
- 方案只来自热门、熟悉或最先想到的范围，未检查实质不同路线；
- 事实、用户陈述、假设、推断、结论没有分开标注；
- 来源未打开、无法定位或不支持原结论；引用的条文编号与原文不符；
- 资格、路线或投入的多个相邻条件共用一个引用，却未逐项核对原文和适用范围；
- 数字单位、分母、时间范围混乱；现金、利润、预收款、可支用资金混用；
- 口头意向、热度、点赞被当成真实需求或付费证据；
- 法规忽略法域、对象、生效日期、例外或属地细则；
- 适用规则取决于未说明的属性，却未确认、未给条件分支（`gap-map.md`）；
- 只指出未知，却没有说明不同答案会造成什么分支后果；
- 未对会阻断路线的未知执行门槛扫描，或扫描后未给出"阻断 / 条件成立 / 尚未核实"三类结论之一；
- 高影响事实没有可直接打开的来源，或来源只有二手摘要时未主动降级、继续当作确定结论使用；
- 只列风险，没有连到验证动作与停止条件；建议无法执行；
- 把未知包装成确定结论；
- 涉及价格、版本、法规、政策、平台规则、软件工具、岗位或市场趋势，未先做时效预判就凭记忆作答；
- 关键数据缺来源强度标注（原始来源 / 可靠转载 / 仅摘要 / 未取得原文），或把转载、摘要写成“已核实原文”；
- 用非当期数据未写年份、对比基线与是否可外推；
- 查不到最新资料却写“目前最新”“最新数据显示”，未写“截至查询日未核实”；
- 把搜索摘要当作原文证据，或未打开原文就断言其内容；
- 展开交付未按 `output-contract.md` §2 的四段式（数据 → 导图 → 总结 → 行动或延伸），或数据区不在最前、结尾区不在最后、结尾类型与用户意图不匹配；用户要求行动时行动区缺六项，用户只想探索时却硬塞执行清单；
- 总结区判断正文超过 300 字，或引用超过 2 个数字，或未区分已核实 / 用户陈述 / 推断 / 未知 / 经验判断；
- 总结区被“已核实”事实列表占满，却没有突出基于证据的判断、理由、反方条件和关键未知；
- 总结区没有先出现清楚的“我的判断”，或没有写反方/不成立条件；
- 数据区没有覆盖会改变排序的主要维度，或没有呈现重要反方证据、错误主张状态和未查缺口；
- 经验判断未标“判断，无单一来源”，或与有来源数据混在同一段，或使用与调研数据同等确定的语气；
- 思维导图不在数据区之后、总结区之前，或未覆盖结论 / 分支 / 依据或未知 / 下一步，或未执行 §2.2 的导图自检；
- 只给一条路线，或多条路线实为同一主线换包装，或路线缺适用条件 / 成本 / 风险 / 放弃什么 / 核心机制与责任位置；
- 只列热门方案，未检查上游供应、下游服务、租赁二手外包合作、缩小承诺、暂缓放弃、替代客户或渠道；
- 给了主推荐，却没写备选更好的条件与切换触发信息；
- 给了主推荐，却没有根据用户处境给条件化引导，或关键条件未知却直接替用户猜偏好；
- 用结构校验表、PASS 清单或字段齐全充当完成证据，却拿不出实际来源原文、计算过程或运行记录；
- 修改只是追加同义提醒，没有处理根因；
- 验收标准自身有错；缺少完整原始记录却声称根因已确定。

## 打回时写清六件事

1. **错在哪里**：引用原产出中的位置与原话；
2. **影响哪个判断**：哪个结论、排序或行动因此不可靠；
3. **根因属于哪类**：执行疏漏 / 流程缺位 / 输入定义不清 / 验收标准错误 / 工具或宿主限制 / 证据不足；
4. **应改哪里**：哪个文件、哪个环节或哪条标准；
5. **怎样验证修改有效**：同条件对比、具体核查或复算；
6. **哪些部分可以保留**：不必重做的部分写明，避免全盘返工。

## 与专题角色的关系

按 `research-specialists.md` 调用专题角色时，其统一交接格式用于角色到主 Agent 的交接；本协议用于对最终产出的把关。两者可以叠加，不互相替代。
